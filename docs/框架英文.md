## Methodology: AI Novel Director Main Workflow Framework 

This section presents the methodology of the AI Novel Director main workflow. As shown in Figure \ref{fig:main_flow}, the system uses the project as the management unit and the chapter as the minimum generation unit, decomposing long-form writing into nine continuous stages: “project and setting organization, chapter contract construction, beat planning, pre-generation review, main text generation, post-generation review, minimal revision, review and commit, and state write-back.”

Unlike one-shot generation of a final text, this framework emphasizes a closed-loop governance process of “structuring first, generating second, validating afterward, and then committing,” enabling long-form serialized writing to continuously evolve within a controllable context scope.

---

### Project and Setting Layer

Given a project $P$ and the current chapter input
$X_n = {title, goal, conflict, hook, tone, wordCount, selectedSettingIds, constraintPolicy}$,
the system first aggregates the project setting database, recent chapters, unresolved foreshadowing, and AI configurations to form the contextual set required for chapter generation $\mathcal{K}_n$.

The setting database includes not only characters, world-building, locations, items, and ability systems, but also structured constraints for continuity and world rules. The goal of this layer is not to directly write the chapter text, but to transform scattered creative intent into a unified input that can be consumed by downstream modules.

---

### Chapter Contract Layer

Based on the contextual set $\mathcal{K}_n$, the system constructs a chapter contract `contract`, explicitly locking in chapter number, title opening line, chapter task, conflict anchor, ending requirements, required settings, required callbacks, continuity constraints, and hard prohibitions. This can be formalized as:

$$
\mathcal{C}*n = f*{\text{contract}}(P, X_n, \mathcal{K}_n)
$$

where $\mathcal{C}_n$ is the hard constraint set for chapter generation.

The core function of this layer is to predefine “what must be written, what must not be written, and how continuity must be maintained,” thereby reducing risks such as character drift, setting violations, and topic deviation.

---

### Beat Planning Layer

The system further translates the chapter contract into an executable chapter plan `plan`, including narrative mode, chapter summary, beat list `beats`, mandatory retention items `mustKeep`, required callbacks `mustMention`, required settings `mustUseSettings`, continuity constraints `continuity`, forbidden elements `forbidden`, and ending mode `endingMode` with ending notes `endingNote`.

When a remote model configuration is available, a planning agent is invoked to generate a structured brief. When unavailable or manually overridden by the user, the system falls back to the local plan while preserving manual edits. The relationship is:

$$
\mathcal{P}*n = f*{\text{plan}}(\mathcal{C}_n)
$$

The goal of this layer is to decompose chapter execution into 3–6 actionable beats, providing a clear progression path for subsequent generation.

---

### Pre-Generation Review Layer

Before generating the main text, the system uses `guard_preflight` to inspect consistency between `contract` and `plan`, checking for setting conflicts, character motivation drift, unresolved foreshadowing, insufficient beats, and unclear ending traction. It outputs scores, issue lists, and minimal repair suggestions:

$$
\mathcal{G}*n^{pre} = f*{\text{guard}}(\mathcal{C}_n, \mathcal{P}_n)
$$

If no manual workflow draft is provided by the user, the system automatically feeds back the review suggestions into the contract and plan to reduce failure probability in generation. This layer acts as a pre-generation gate, ensuring that chapter goals are stable before entering writing.

---

### Main Text Generation and Post-Review Layer

In the generation stage, a `writer` model produces the chapter text $D_n$ based on the contract, plan, and setting database. If remote models are unavailable, a rule-based fallback generator is used.

After generation, the system enters a `guard` stage again to check for setting conflicts, motivation drift, missing foreshadowing callbacks, chapter opening drift, and weak ending hooks, producing a `repairPlan`:

$$
D_n = f_{\text{writer}}(\mathcal{C}_n, \mathcal{P}_n), \quad
\mathcal{G}*n^{post} = f*{\text{guard}}(D_n, \mathcal{C}_n, \mathcal{P}_n)
$$

Post-review is not intended for full rewriting, but for identifying minimal correction points while preserving story facts, structural rhythm, and chapter identity.

---

### Minimal Revision and Review Commit Layer

When post-review identifies content-level issues, the system triggers `repair`, applying only localized edits to necessary passages without altering established narrative facts:

$$
\tilde{D}*n = f*{\text{repair}}(D_n, \mathcal{G}_n^{post})
$$

The revised text is not immediately written into the main database. Instead, it is packaged into a `review_session`, where the user can choose to `commit` or `discard`.

This design decouples “generated output” from “formal persistence,” reducing the risk of incorrect model outputs contaminating the main storyline while preserving human final authority.

---

### Persistence and State Write-Back Layer

Once a review session is committed, the system performs chapter persistence, version backup, project state updates, story state event logging, and I/O logging.

Story state events `story_state_events` are extracted from the chapter and metadata, including activated settings, relationship changes, foreshadowing progression, world-rule reminders, next-chapter pressure, and affected chapters, forming a timeline for long-form serialization. I/O logs preserve inputs and outputs at each stage for debugging, prompt analysis, and revision tracing.

This forms a complete closed loop from structured input to reviewable output and state feedback.

---

### Extended Workflows

In addition to chapter generation, the system reuses the same recording and governance mechanisms to support auxiliary workflows such as setting extraction, polishing/modification, and chapter inspection.

Specifically, setting extraction reverses stable settings from chapter text; polishing modifies expression while preserving facts and settings; and chapter inspection outputs risk scores and issue summaries for the latest chapter.
